ОТЧЁТ ПО МОДЕЛИ GUARD: НАЙДЕННЫЕ ПРОБЛЕМЫ, ИСПРАВЛЕНИЯ И РЕЗУЛЬТАТЫ
=====================================================================
Дата: 07.11.2026
Модель: RandomForestClassifier (scikit-learn 1.9.0)
Датасет: malicious_phish_cleaned.csv (642 861 URL, 4 класса:
         benign / defacement / malware / phishing)


1. ИСХОДНОЕ СОСТОЯНИЕ
---------------------
Старая модель: RandomForest(n_estimators=100, max_depth=12,
class_weight='balanced'), 48 признаков.
Заявленная точность: accuracy = 0.9311.

На реальных сайтах модель работала плохо. Пример (вероятности классов):
  https://www.bbc.com/news  -> benign 0.00, phishing 0.64
  http://www.bbc.com/news   -> benign 0.00, defacement 0.62
  https://example.com/      -> benign 0.00, phishing 0.88
Получалось, что любой обычный сайт с "https://" выглядел опасным.


2. НАЙДЕННЫЕ ПРОБЛЕМЫ
---------------------

2.1. Утечка метки через формат записи URL (критично)
  Распределение схемы URL по классам в датасете:

    класс        http://   https://   без схемы
    benign        33 428     1 950     392 725
    defacement    96 457         0           0
    malware       24 546     6 764       1 210
    phishing      17 593     6 329      61 859

  Аналогично с "www.": он есть у 70% defacement-URL и только у 3% benign.
  Модель выучила правило "есть схема / www -> не benign" вместо
  реальных признаков фишинга. Расширение же всегда отправляет
  "https://...", поэтому любой сайт получал низкую вероятность benign.
  Кроме того, без схемы urlparse() не находит hostname, и в обучении
  все признаки по хосту (дефисы, триггеры в хосте, длина хоста)
  были равны 0, а при работе расширения - нет.
  Из-за этой утечки accuracy 0.93 была завышена.

2.2. Перекос в классе benign
  Benign-URL в датасете - в основном длинные глубокие ссылки с
  нескольких крупных сайтов (youtube.com - 8 617, amazon.com - 4 618).
  Медианная длина: benign 46 символов, phishing 31 символ.
  Среди URL без пути (просто домен) 23 086 phishing против 47 632 benign,
  при этом главных страниц популярных сайтов почти нет
  (bbc.com - 0, wikipedia.org - 0).
  Модель выучила правило "короткий URL = фишинг".
  class_weight='balanced' дополнительно усиливал класс phishing и
  увеличивал число ложных срабатываний.

2.3. Сервер возвращал не ту вероятность (критично)
  В check_isPhishing.py искался класс 'malicious', которого в модели
  нет (классы: benign, defacement, malware, phishing). Код брал
  индекс 1 = defacement, то есть API возвращал P(defacement), а не
  вероятность опасности. Пример: для https://example.com/ модель
  давала P(phishing)=0.88, а API отдавал 0.04.

2.4. Дубликаты и противоречивые метки
  10 065 точных дубликатов URL. После приведения URL к единому виду
  найдено 3 813 URL с разными метками классов одновременно.
  Дубликаты, попавшие и в train, и в test, завышают метрики.

2.5. Ошибки в скрипте обучения
  - В закоммиченной версии train_GUARD.py не запускался:
    "from pathlib import path", "randomforestclassifier", "pd.dataframe".
  - Модель сохранялась в backend/coursework.pkl, а сервер загружал
    backend/ml/coursework.pkl - после переобучения сервер продолжал
    использовать старую модель.

2.6. Сбой на некорректных URL
  URL с символом "[" в датасете вызывали ValueError("Invalid IPv6 URL")
  в urlparse() и обрывали извлечение признаков.

2.7. Размер модели
  RandomForest без ограничений на 670 тыс. строк весит 249 МБ:
  не помещается в GitHub (лимит 100 МБ) и в 512 МБ RAM бесплатного
  тарифа Render.

4.5. Правила поверх модели (backend/check_rules.py)
  Модель пропускала очевидный фишинг (paypal-login-verify.xyz -> 0.33),
  потому что в датасете мало таких примеров. Добавлен слой правил;
  итоговая вероятность = max(модель, правила). Сервер дополнительно
  возвращает поле reasons - список сработавших правил (на украинском).

  Правила (оценка; порог блокировки 0.6):
    - "@" в адресе (http://paypal.com@evil.ru)               0.85
    - IP-адрес вместо домена (кроме локальных 192.168.*)      0.75
    - название бренда на чужом домене + триггер в домене,
      подозрительная зона или бренд в поддомене
      (paypal.com.evil.ru, privat24-ua.online)                0.90
    - подозрительная зона + слово-триггер в самом домене      0.70
    - 3+ уровня поддоменов + слова-триггеры                   0.65
    - только бренд в домене (amazongames.com), punycode       0.50
      (только как причина, не блокирует)
  Популярные (Tranco) и официальные домены брендов правилами не
  проверяются. Бренды включают украинские банки (privatbank, privat24,
  monobank). Короткие бренды (apple, ups, citi) ищутся как отдельное
  слово, чтобы "groups" и "pineapple" не срабатывали.

  Проверка на ложные срабатывания на реальных сайтах, которых нет ни
  в обучении, ни в списке доверенных (Tranco, места 50 001-60 000,
  10 000 URL, к 2/9 добавлены /login, /account, /signin):
    FPR модели           0.0154
    FPR правил           0.0000
    FPR модель+правила   0.0154
  Первая версия правил давала здесь 1.3% ложных срабатываний
  ("зона .pro/.info + /login в пути", "amazongames.com",
  "huaweicloud" содержит "icloud", тайские punycode-домены);
  правила были ужесточены.

  На тестовой выборке датасета (только исходные строки):

    модель            0.9483   0.6547  0.0168

4.6. Исправления расширения
  а) Полный URL на сервер
     Раньше server_worker.js отправлял normalizeUrl(url) - только
     origin + path, и признаки по query (триггеры, доли "?", "=", "&")
     в работе всегда были 0, хотя модель обучена с ними. Теперь
     отправляется URL без #якоря, но с параметрами. Белый список
     по-прежнему сравнивает origin + path.

  б) Проверка до загрузки страницы
     Раньше: content.js запускался на каждой странице, отправлял
     service worker'у сообщение state_changed, тот проверял URL и, если
     сайт фишинговый, просил content.js показать confirm(). Проблема:
     к этому моменту страница уже загружена - пользователь видит
     фишинговый сайт и может ввести данные, а блокировка правилом
     declarativeNetRequest срабатывает только при следующем открытии.
     Теперь: service worker сам слушает webNavigation.onBeforeNavigate
     (событие до начала загрузки, разрешение webNavigation уже было в
     manifest.json) и при угрозе перенаправляет вкладку на
     frontend/blocked.html - страницу-предупреждение с кнопками
     "Закрити вкладку" и "Все одно перейти" (снимает блокировку и
     добавляет URL в белый список).

  в) Удалён content.js
     Обе его функции перешли в другие места: запуск проверки - в
     onBeforeNavigate в service worker, предупреждение - на страницу
     blocked.html. Если бы content.js остался, каждый сайт проверялся
     бы дважды (onBeforeNavigate + state_changed от content.js), а
     пользователь видел бы и страницу-предупреждение, и confirm().
     Кроме того, content script со совпадением <all_urls> внедряется в
     каждую страницу - без него расширение легче и требует меньше
     доступа к содержимому сайтов. Из manifest.json убран раздел
     content_scripts.

  г) Исправлен .gitignore
     Был сохранён в UTF-16, Git его не читал - в репозиторий попали
     __pycache__/*.pyc. Пересохранён в UTF-8, .pyc удалены из
     репозитория.


4.7. Проверка перенаправлений (check_ssl_and_redirects.py)
  Исходный модуль (check_ssl + check_redirects) не использовался.
  Разбор:
  - check_ssl: наличие HTTPS почти ничего не говорит - большинство
    фишинговых сайтов давно используют бесплатные сертификаты Let's
    Encrypt. Возраст сертификата обманчив: Let's Encrypt перевыпускает
    сертификаты каждые 60-90 дней, поэтому и у нового фишинга, и у
    bbc.com он меньше 90 дней. Невалидный сертификат - сильный признак,
    но Chrome сам показывает на это полноэкранное предупреждение.
    Поэтому check_ssl не использовался, а 10.11.2026 удалён: он
    подключался к адресу пользователя без проверки на SSRF.
  - check_redirects: количество перенаправлений - слабый признак
    (обычные сайты перенаправляют по 3-5 раз при входе, рекламе,
    сокращении ссылок). Полезен другой вопрос: КУДА ведёт ссылка
    (bit.ly/xxx -> paypal-login-verify.xyz). Ни модель, ни правила
    конечный адрес не видят, а bit.ly - популярный домен.

  Новая check_redirects:
  - идёт по перенаправлениям вручную (GET без загрузки тела, таймаут
    2 с, не более 5 шагов) и возвращает конечный URL;
  - защита от SSRF: API публичный и без авторизации, поэтому перед
    каждым шагом проверяется, что адрес публичный (не localhost,
    не 192.168.*, не 169.254.169.254 и т.п.), и только http/https.
    Шаги делаются вручную, а не allow_redirects=True, чтобы
    перенаправление на внутренний адрес тоже блокировалось.

  Как считается итоговая оценка (каскад):
    score = max(модель(url), правила(url))
    если url - сокращённая ссылка или 0.3 <= score < 0.6 ("серая зона"):
        конечный = check_redirects(url)
        если домен конечного != исходного:
            score = max(score, модель(конечный), правила(конечный))
  Новых весов нет: конечный адрес проверяется той же моделью и
  правилами, качество которых уже измерено. Подобрать веса для
  "сертификат / число редиректов" нельзя - большинство фишинговых
  URL из датасета давно не работают, проверить их вживую невозможно.
  Дорогая сетевая проверка запускается только когда есть сомнения:
  на незнакомых сайтах (Tranco 50-55k) - в 17% случаев, обычно
  ~0.3 с. Остальные запросы отвечаются за ~0.01 с.

  Пример: https://bit.ly/abc123 -> paypal-login-verify.xyz/signin
    -> 0.9, причины: "перенаправляє на paypal-login-verify.xyz", ...


4.8. Google Safe Browsing (safebrowsing.py)
  Модель и правила оценивают, как URL ВЫГЛЯДИТ; Safe Browsing - есть ли
  URL в базе известных угроз Google. Проверки дополняют друг друга:
  - новый фишинг (первые часы) в базе ещё отсутствует - его ловит
    модель/правила по виду адреса;
  - фишинг с "обычным" адресом и взломанные сайты по виду URL не
    определить - их ловит Safe Browsing, если они уже в базе.
  Архитектура: база известных угроз + ML для новых.

  Подключение: если URL найден в базе -> вероятность 1.0, причина
  "є в базі Google Safe Browsing". Ключ API хранится в backend/.env
  (в .gitignore) и в переменной окружения GSB_API_KEY на Render;
  ключ ограничен только Safe Browsing API. Без ключа проверка
  пропускается. Лимит бесплатного API - 10 000 запросов в сутки.
  Исправлен баг: при ответе не 200 (неверный ключ, лимит) функция
  возвращала None вместо False.

  Проверка (тестовые адреса Google, всегда числятся в базе):
    http://testsafebrowsing.appspot.com/s/phishing.html  -> 1.0
    http://testsafebrowsing.appspot.com/s/malware.html   -> 1.0
    https://www.bbc.com/news                             -> 0.04
  Время ответа сервера выросло с ~0.01 с до ~0.15 с (запрос к Google).
  Точность на датасете измерить нельзя: старые URL из датасета давно
  удалены из базы Google.


4.9. Ограничение частоты запросов (app.py)
  API публичное и без авторизации: кто угодно мог скриптом нагрузить
  сервер или израсходовать дневной лимит Google Safe Browsing
  (10 000 запросов). Добавлен Flask-Limiter: не более 60 запросов в
  минуту с одного IP, дальше ответ 429 в формате JSON. Так как на
  Render запросы идут через прокси, реальный IP клиента берётся из
  X-Forwarded-For (werkzeug ProxyFix), иначе лимит был бы общим для
  всех пользователей. Для обычного пользователя 60 переходов в минуту
  с запасом, к тому же расширение кэширует ответы на 30 минут.
  Пиковая память сервера: 440 МБ (+3 МБ).

  Также к Google Safe Browsing больше не обращаемся, если модель или
  правила уже заблокировали сайт: ответ быстрее, лимит тратится
  медленнее.

4.10. Тесты (backend/tests/test_guard.py, pytest)
  29 тестов, ~6 с, без интернета (Safe Browsing и перенаправления
  подменены заглушками):
  - признаки: 47 штук; URL с https://www. и без даёт одинаковые
    признаки (защита от возврата утечки из п. 2.1); битые URL не

4.11. Исправления по аудиту безопасности (OWASP Top 10)
  Проведена проверка проекта по OWASP Top 10. Исправлено:
  - Обход защиты от SSRF (check_ssl_and_redirects.py). Адрес
    "http://127.0.0.1\@bit.ly/" urlparse читал как bit.ly (публичный),
    а requests подключался к 127.0.0.1. Так как bit.ly - сокращатель,
    сервер всегда шёл по такой ссылке: один запрос к API давал GET на
    localhost или внутреннюю сеть Render. Теперь хост берётся тем же
    разбором, что и в requests (urllib3 parse_url). Кириллические
    домены (пример.рф) проверяются как раньше.
  - Разрешены только порты 80 и 443: раньше через сервер можно было
    сканировать порты чужих хостов (http://8.8.8.8:22/).
  - Общий лимит времени 4 с на проверку перенаправлений: timeout=2 в
    requests действует на каждое чтение отдельно, и медленный сервер
    держал запрос 12 с и дольше.
  - Падение сервера по памяти (app.py). Размер тела и длина URL не
    ограничивались: один URL на 20 МБ поднимал пик памяти с 428 до
    815 МБ при лимите Render 512 МБ. Теперь тело > 16 КБ - ответ 413,
    url не строка, пустой или длиннее 2048 символов - 400 (раньше 500).
    Пиковая память после правок: 427 МБ, при запросе на 20 МБ не растёт.
  - Убран CORS(app): разрешал запросы к API с любого сайта, т.е. любой
    сайт мог заставить браузеры посетителей слать запросы (каждый со
    своего IP, лимит по IP не помогал). Расширению CORS не нужен -
    service worker обращается к серверу через host_permissions.
  - Суточный лимит 1000 запросов с IP: 60 в минуту - это до 86 400 в
    сутки, а квота Google Safe Browsing 10 000. После её исчерпания
    проверка по базе Google молча отключается до конца суток.
  - Клиенту при ошибке больше не возвращается текст исключения.
  Тестов стало 36 (+7: обход SSRF, нестандартный порт, неверный url,
  слишком большое тело).
  Исправлено по итогам code review (09.11.2026):
  - DNS rebinding: домен резолвился дважды - при проверке и при
    запросе, и во второй раз мог вернуть внутренний IP. Теперь
    подключение идёт к уже проверенному IP (urllib3 напрямую вместо
    requests), имя хоста передаётся для SNI и проверки сертификата.
  - IPv6 с вложенным IPv4 (::127.0.0.1, NAT64 64:ff9b::a9fe:a9fe)
    is_global считал публичными - теперь проверяется вложенный IPv4.
  - Лимит 4 с: проверялся только в начале шага, и один медленный
    шаг мог занять ~4 с сверх него. Теперь каждый запрос получает
    общий таймаут min(оставшееся время, 2 с).
  - Некорректный JSON или Content-Type давал HTML-ошибку вместо JSON
    с кодом 400 (get_json(silent=True)).
  Тестов стало 39 (+3: IPv6-формы внутренних адресов).
  Остаточные риски: сервер сам открывает URL из серой зоны
  (одноразовые ссылки); лимит запросов хранится в памяти и
  сбрасывается при перезапуске; у резолва DNS нет своего таймаута;
  не проверено, сколько прокси стоит перед сервером на Render
  (ProxyFix(x_for=1)) - от этого зависит, работает ли лимит по IP.
  check_ssl (не использовался, без проверки на SSRF) удалён.

4.13. Поддержка Firefox
  Firefox (с версии 128) поддерживает Manifest V3 и пространство
  имён chrome.*, поэтому код расширения почти не менялся:
  - manifest.json: Firefox не поддерживает background.service_worker,
    добавлен background.scripts с тем же файлом (Chrome берёт
    service_worker, Firefox - scripts);
  - browser_specific_settings.gecko: ID расширения, минимальная
    версия 128, data_collection_permissions = browsingActivity
    (честно указано, что адреса сайтов уходят на сервер; требуется
    для публикации на addons.mozilla.org);
  - server_worker.js: страницы расширения в Firefox имеют адрес
    moz-extension:// - они тоже не отправляются на проверку.
  Проверка в Firefox 158 (headless, расширение загружено как
  временное): http://paypal-login-verify.xyz/signin ->
  moz-extension://.../blocked.html, www.bbc.com/news открывается.
  Попап при ширине 280 px - ничего не выходит за край. Chromium 155
  упаковывает расширение с новым манифестом без ошибок.
  Ограничение: без подписи Mozilla расширение ставится только
  временно (about:debugging) и пропадает после перезапуска.

5.3. Модель анализирует только строку URL
  Модель не видит содержимое страницы и SSL-сертификат: фишинг на

  отличить. Частично это закрывает Google Safe Browsing (п. 4.8).
  Редиректы проверяются отдельно от модели (п. 4.7) - только для
  коротких ссылок и "серой зоны".

5.4. Проверка не мгновенная
  webNavigation.onBeforeNavigate не может остановить загрузку
  страницы, только перенаправить вкладку после ответа сервера. Если
  сервер отвечает медленно (Render "просыпается" после простоя
  ~30-60 с), фишинговая страница может успеть показаться.

5.5. Прочее
  - Модель (29 МБ) и датасет (44 МБ) хранятся в репозитории.
  - Все посещаемые URL отправляются на публичный сервер без
    авторизации (вопрос приватности).


6. ПЕРСПЕКТИВЫ РАЗВИТИЯ
-----------------------
Не реализовано, описаны возможные направления.

6.1. База ссылок и регулярное переобучение
  Сервер сохраняет проверенные URL и вердикты в БД (например,
  PostgreSQL). Известные ссылки отдаются из базы сразу, модель
  проверяет только новые. Модель переобучается по расписанию (раз в
  сутки/неделю), а не после каждой ссылки: RandomForest в scikit-learn
  не поддерживает дообучение (warm_start только добавляет деревья), а
  фишинговые приёмы меняются за недели, так что этого достаточно.
  Новая версия выкатывается, только если метрики на отложенной выборке
  не хуже прежних; старые версии хранятся для отката.
  Обучение - отдельной задачей, не на Render (512 МБ RAM, сервер уже
  занимает ~440 МБ).
  Источники меток: PhishTank, OpenPhish, URLhaus, Google Safe Browsing
  (п. 4.8), проверенные жалобы пользователей. Учить модель на её же
  вердиктах нельзя - она закрепит свои ошибки.
  Приватность: хранить домен и путь без параметров (в них бывают
  токены и email), согласие пользователя, политика конфиденциальности
  (требование GDPR и Chrome Web Store), срок хранения.

6.2. Обратная связь от пользователей
  При срабатывании GUARD пользователь выбирает "перейти" или "назад".
  Этот выбор можно сохранять (URL, домен, скор модели, выбор, хэш ID
  установки, время) и считать по уникальным пользователям в разрезе
  домена. Но использовать его напрямую как метку нельзя:
  - жертва фишинга уверена, что сайт настоящий, поэтому на хорошей
    подделке "перейти" нажмут чаще всего - это систематическая
    ошибка, частота её не исправит;
  - отзыв собирается только по срабатываниям, о пропущенном фишинге
    данных нет; обучение на таких данных делает модель мягче;
  - голоса можно накрутить множеством установок.
  Поэтому выбор пользователя - сигнал для проверки, а не истина.
  Ложной тревогой домен считается, только если сходятся независимые
  признаки: >= K уникальных пользователей и >= X% из них нажали
  "перейти", Google Safe Browsing чист, домен старый или есть в
  top-1m. Такие домены идут в белый список и на ручную проверку, в
  обучение - только подтверждённые. Явная кнопка "GUARD ошибся" и
  "пожаловаться на сайт" (на любой странице, для пропущенного фишинга)
  дают более сильный сигнал. Общие хостинги (github.io,
  sites.google.com, vercel.app) обрабатываются отдельно.

6.3. Блокировка на уровне DNS
  Работает для всех приложений и устройств в сети, без расширения
  (корпоративные сети, школы, родительский контроль). Ниша - локальный
  украинский фишинг (поддельные OLX, Нова Пошта, Приват, Дія), который
  глобальные списки ловят с опозданием.
  Отличия от расширения:
  - DNS видит только домен. Около половины текущих признаков (путь,
    параметры: path_trigger_count, query_trigger_count, slash_ratio,
    url_entropy и т.д.) недоступны - нужна отдельная модель только по
    домену, она будет слабее. Проверки SSL и редиректов нет.
  - Ответ нужен за миллисекунды, поэтому модель не вызывается на
    каждый запрос: известные домены - из списка/кэша, новые
    оцениваются в фоне (первый запрос проходит, следующие
    блокируются) или заранее (новые домены, Certificate Transparency).
  - Ошибка дороже: сайт просто не открывается, кнопки "перейти" нет.
    Порог нужен строже.
  Ограничения: бесплатный Render принимает только HTTP (нужен UDP 53)
  и засыпает после простоя; браузеры с DNS-over-HTTPS обходят
  системный DNS.
  Варианты от простого к сложному:
  1) GUARD генерирует блоклист, блокирует готовый резолвер (Pi-hole,
     AdGuard Home, RPZ для Unbound/BIND) - реально как прототип;
  2) свой резолвер-прокси (CoreDNS, dnsdist, Python + dnslib) с кэшем и
     фоновой оценкой новых доменов;
  3) свой DoH-сервис с аккаунтами - уже коммерческий продукт.
  DNS - первый, грубый слой; расширение остаётся для проверки полного
  URL и страницы. Уровни дополняют друг друга.
